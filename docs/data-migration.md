# 데이터베이스·파일 저장소 이전 안내

현재 서버는 SQLite를 사용합니다. 이 문서는 데이터와 첨부 파일을 보존해 PostgreSQL 또는 다른 DB로 옮기는 준비 절차입니다. **연결 주소만 바꾸면 기존 서버가 PostgreSQL로 실행되는 것은 아닙니다.** 전체 서버의 SQLite 쿼리·스키마 초기화·동기 DB 호출을 대상 DB 드라이버에 맞게 교체하고 검증해야 합니다. 아래 내보내기 도구는 그 작업에 사용할 실제 데이터와 PostgreSQL용 SQL을 제공합니다.

## 저장 구조와 교체 지점

- 파일 내용: `.data/uploads/<임의의 storage_key>`에 저장합니다. `PINGO_UPLOAD_DIR`로 변경합니다. 공개 정적 경로가 아닙니다.
- 파일 메타데이터: `attachments` 테이블에 메시지 ID, 파일 ID, 원본 이름, 크기, MIME, SHA-256, 저장 키를 저장합니다. 바이너리나 절대 경로를 DB에 저장하지 않습니다.
- `file-store.mjs`: 비동기 `put(readable, {name,maxBytes})`, `open(key)`, `remove(key)` 계약을 제공하는 로컬 파일 어댑터입니다. S3 등의 객체 저장소 구현으로 교체할 지점입니다. `open`은 `{stream,size}`를 반환해야 하며 객체는 비공개여야 합니다.
- `attachment-repository.mjs`: 첨부 메타데이터와 파일 메시지 게시 트랜잭션을 담당하는 SQLite 어댑터입니다. 비동기 `find`, `publish`, `decorateMany`, `decorateMessage` 계약으로 분리했습니다. 대상 DB에서는 중복 전송 방지와 용량 검사, 메시지·파일 메타데이터의 원자적 저장을 유지해야 합니다.
- `attachments.mjs`: 저장소 종류와 분리된 권한·차단·전송·다운로드 처리입니다. 참여 권한 검사 후에만 비공개 파일 스트림을 제공합니다.

기존 파일 ID, 메시지 ID, 사용자 ID와 저장 키를 보존하면 채팅 기록의 다운로드 링크를 유지할 수 있습니다.

## 내보내기

운영 DB와 파일을 먼저 백업하고, 쓰기 트래픽이 낮거나 서비스를 중지한 시간에 실행하세요. 원본 DB는 읽기 전용 트랜잭션으로 읽고 변경하지 않습니다. 파일은 불변 객체로 복사하며 크기와 SHA-256을 검증합니다. 읽기 트랜잭션이 오래 유지되면 SQLite WAL이 커질 수 있습니다.

```sh
# 기본 DB와 파일 저장 경로를 사용하는 경우
npm run export-data -- /private/pingo-export

# 별도 영구 저장 경로를 사용하는 경우
PINGO_DB_PATH=/persistent/pingo.sqlite PINGO_UPLOAD_DIR=/persistent/uploads \
  npm run export-data -- /private/pingo-export
```

출력 폴더는 존재하지 않아야 하며 기존 출력은 덮어쓰지 않습니다. 도구가 만든 폴더는 0700, 파일은 0600 권한으로 생성합니다. 실패하면 도구가 이번에 만든 미완성 출력만 정리합니다.

출력 내용:

- `manifest.json`: 버전, 테이블별 건수·열 정보·외래키, 첨부 파일별 크기·체크섬
- `tables/*.jsonl`: 행별 JSON 데이터. 다른 DB의 ETL·가져오기 작업에 사용할 수 있습니다.
- `postgres.sql`: PostgreSQL 테이블, 체크·고유·외래키 제약, 데이터, 인덱스, 자동 증가 시퀀스 복원 SQL
- `files/<storage_key>`: 검증한 원본 첨부 파일

**로그인 세션 데이터는 내보내지 않습니다.** 대상 SQL에는 비어 있는 세션 테이블을 만들며, 전환 후 사용자는 다시 로그인해야 합니다. 비밀번호 salt·해시, 복구 코드 해시, 대화·차단·신고 증거 등이 포함되므로 이 출력은 민감한 비공개 백업입니다. GitHub, 공개 버킷, 화면 캡처, 개발 환경 게시 스냅샷에 넣지 마세요.

도구는 현재 앱의 TEXT·INTEGER 스키마를 변환합니다. PostgreSQL TEXT에서 표현할 수 없는 NUL 문자열, BLOB·지원하지 않는 스키마, 안전하게 표현할 수 없는 정수는 오류로 중단하며 원본을 변조하지 않습니다.

## PostgreSQL로 데이터 가져오기

1. 빈 PostgreSQL 데이터베이스와 비공개 파일 저장 공간을 준비합니다. 기존 운영 DB 위에 실행하지 마세요.
2. 표준 PostgreSQL 접속 설정으로 연결한 터미널에서 실행합니다. 비밀번호를 명령문에 직접 적지 마세요.

```sh
psql -v ON_ERROR_STOP=1 -f /private/pingo-export/postgres.sql
```

SQL은 하나의 트랜잭션으로 실행합니다. 테이블이 이미 존재하는 등의 오류가 나면 가져오기를 중단합니다. ID를 그대로 가져오고 시퀀스도 갱신하므로 다음 메시지 ID가 충돌하지 않도록 합니다.

3. `manifest.json`의 각 테이블 건수와 대상 DB의 건수를 비교합니다. 파일별 크기·SHA-256도 비교합니다.
4. 로컬 저장소를 계속 사용하면 `files/`의 내용을 새 비공개 업로드 폴더로 옮기고 `PINGO_UPLOAD_DIR`를 설정합니다. 객체 저장소로 옮기면 같은 `storage_key`로 업로드하고 저장소 어댑터를 연결합니다. 공개 URL을 메타데이터에 대신 넣지 마세요.
5. 앱의 DB 연결과 모든 SQLite 쿼리를 대상 드라이버로 전환합니다. PostgreSQL BIGINT 반환값의 숫자 변환, 바인딩 문법, 트랜잭션·제약·스키마 초기화도 확인해야 합니다. 이 서버 전환 작업은 아직 구현하지 않았습니다.
6. 복제된 환경에서 로그인, 친구, 차단, 1:1·단체 대화, 과거 기록, 파일 전송·다운로드·접근 거부, 신고·운영자 CLI를 검증합니다. 새 메시지·첨부 ID 생성과 동시 전송도 확인합니다.
7. 쓰기를 중지하고 마지막 데이터를 내보낸 뒤 전환합니다. 구버전 서버가 원본 DB에 계속 쓰지 않도록 종료하고, 검증된 원본 백업과 되돌릴 절차를 보관합니다.

생성된 SQL은 임시 데이터로 PGlite(PostgreSQL 호환 엔진)에 실제 가져오기해 테이블 건수와 시퀀스를 검증했습니다. 외부 운영 PostgreSQL·네트워크·권한·대용량 부하는 아직 검증하지 않았습니다. SQLite의 실시간 알림은 단일 프로세스 기준이므로 여러 서버로 확대할 때 Redis 등의 이벤트 전달 계층도 필요합니다.

## 파일 운영 제한

현재 파일당 20MB, 사용자당 누적 200MB, 서버 전체 누적 2GB입니다. 사용자당 분당 전송 시도 20회, 동시에 사용자당 2개·서버 전체 8개를 허용합니다. 방 숨기기는 파일 삭제가 아니므로 용량이 반환되지 않습니다. 삭제·보관 기간·관리자 정리는 별도 정책과 구현이 필요합니다.

지원 확장자와 기본 시그니처·텍스트 UTF-8 검사는 악성코드 검사나 압축 내부 검사와 다릅니다. 공개 운영 전 바이러스 검사·검역 저장소와 보관·삭제 정책을 검토하세요. 미완료 업로드는 정상 오류·취소 시 정리하지만 프로세스가 강제 종료되면 `.upload-*` 임시 파일이나 DB에 연결되지 않은 파일이 남을 수 있습니다. 실제 업로드가 없는 중지 시간에만 정리하고 디스크 사용량을 감시하세요. DB와 파일 저장소를 함께 백업해야 복원 후 다운로드가 유지됩니다.
